# 34-R19b-a1 - RAI technical review (PyRel idioms, ontology, rules and graph, explanations)

Reviewer: R19b, fresh context, skeptical stance. Static review only. The only commands run were local `.venv/bin/python` introspection of relationalai 1.27.1 and one throwaway in-memory model in /tmp that printed field orders. Nothing was sent to the RAI engine or to Snowflake, because the P5 reload is in progress.

I judged the code against the skills rai:rai-pyrel, rai:rai-graph-analysis and rai:rai-ontology, and against the installed package. Where the skill and the package disagree, the package wins (research/pyrel_cheatsheet.md section 14).

**STATUS: FAIL** (0 BLOCKER, 3 MAJOR, 15 MINOR)

## Verdict in brief

- The work is real, not SQL in disguise:
  - Recursive closure with nested negation decides thesis membership.
  - A three-way dated join scores the PE-backed CFO.
  - Knows is assembled from three typed evidence sources, then BFS distance is computed over it.
  - Exact Brandes betweenness feeds a governed coverage-gap rule.
  - A graph distance (`nearest_seed_hops`) feeds the Finale rule.
- Idioms are mostly well chosen for the 1.27.1 legacy compiler: two-rule defaults, unique rank tie-breaks, refs for same-type slots, `| 0` only on aggregates, and exact pivots.
- The three MAJOR findings:
  - **M1:** two Properties declare a false functional dependency.
  - **M2:** an empty graph output silently becomes a wrong business answer.
  - **M3:** the live Finale has no safe extension point, and the skill-vs-package traps are not given to the presenter session.

## MAJOR

### M1. MAJOR - `Person.dm_hops` and `Company.commercial_hops` declare a false functional dependency, and the compiler emits it to the engine

- **Where:**
  - core.py:430 `Person.dm_hops = model.Property(f"{Person:decision_maker} is {Integer:hops} hops from {Person:person}")`
  - core.py:461 `Company.commercial_hops = model.Property(f"{Company:subject} is {Integer:hops} commercial links from {Company:company}")`
- **What is actually wrong:**
  - The fields are not bound to the wrong slots. Every call site uses the declared order consistently:
    - graphs.py:157, 190 and 345
    - rules.py:764
    - scripts/check_graphs.py:174, 223 and 232
  - I confirmed the order on a throwaway model: `['decision_maker', 'hops', 'person']` and `['subject', 'hops', 'company']`.
  - The defect is the functional dependency. A Property makes all fields but the last a key, so these declarations say "(decision_maker, hops) determines one person" and "(subject, hops) determines one company". Both are false: every decision-maker and every bid subject has many neighbours at distance 1.
- **How the package uses it:**
  - `frontend/front_compiler.py:1474-1482` adds `unique_fields(fields[:-1])` for every Property with more than one field.
  - The legacy LQP pass `backends/legacy_lqp/rewrite/function_annotations.py` turns that into `@function(:checked)` on the stored relation.
  - The constraint itself is discharged, because `emit_constraints` is off, so nothing raises. The engine still receives a functional annotation that is false.
  - Today the engine keeps all rows (handoff 21: Pinewick and Cobbleton both sit at 1 hop). We are relying on undefined behavior. The one run that returned 0 `commercial_hops` rows (handoff 21, INFO) is unexplained. A stream resync is plausible, but this annotation is not ruled out.
- **Secondary issue:** the last field's name (`person`, `company`) differs from the attribute name (`dm_hops`, `commercial_hops`), unlike every other multi-field Property in the model. `Person.seed_hops` has the same naming mismatch (core.py:428), but its dependency is correct.
- **Fix:**
  - Put hops last and name it after the attribute:
    - `Person.dm_hops = model.Property(f"{Person:decision_maker} reaches {Person:person} in {Integer:dm_hops} hops")`
    - `Company.commercial_hops = model.Property(f"{Company:subject} reaches {Company:company} in {Integer:commercial_hops} commercial links")`
  - Then update, in one change:
    - graphs.py:157 to `Person.dm_hops(t, m, h)`
    - graphs.py:190 to `Person.dm_hops(n[length], n[i], dd)`
    - graphs.py:345 to `Company.commercial_hops(s, c, h)`
    - rules.py:764 to `Company.commercial_hops(s, c, h)`
    - scripts/check_graphs.py:174, 223 and 232
    - ONTOLOGY.md section 5
  - Re-run check_graphs and the tests. Declaring both as `model.Relationship` also works, but the reorder keeps the contract types.

### M2. MAJOR - An empty graph output becomes a confident wrong answer on stage (a false all-clear in Act 4, a false "cold" in Act 2)

- **Where:**
  - queries.py:408-437 (`q_conflict` exposures)
  - queries.py:245-351 (`q_path`)
  - queries.py:363-402 (`q_flow`)
  - demo_workspace/ask.py (no guard there either)
- **What goes wrong:** no hero function checks that the graph outputs it reads exist.
  - If `Company.commercial_hops` comes back empty, as it did once, `q_conflict` returns zero exposures. Claude Code then tells the room "no conflict with anything we own" while the concentration part still renders. That is the worst possible failure for a conflicts check.
  - If `Person.seed_hops` is empty, every decision-maker gets a "Cold: no path within 3 hops" row with a plausible `why`. That is a false narrative.
  - The tests catch this in a test run, but nothing catches it live.
- **Fix:** add a cheap invariant check at the top of each graph-backed hero function. On failure, retry once after about 20 s, then raise a clear error such as `GraphOutputMissing: commercial graph returned no rows; use fallback`, so the presenter switches to the fallback instead of reading out a wrong answer.
  - (a) `q_conflict`: `distance(from_=...)` always contains the subject's own 0-hop row. Assert that `Company.commercial_hops(s, s, 0)` exists for every ConflictSubject (after M1, `commercial_hops(s, s, 0)`).
  - (b) `q_path`: assert that `Person.seed_hops(seed, seed, 0)` exists for at least one OurSeed and that `count(Knows) > 0`.
  - (c) `q_flow`: assert that at least one `Intermediary.bridge_rank` exists.
  - Also make `make warm` compare the answer sets to golden (this matches R19d m3), so a resync after warm-up is caught before the room is.

### M3. MAJOR - The live Finale has no safe extension point, and the presenter session is not told about the 1.27.1 traps that the skills contradict

- **Where:**
  - demo_workspace/CLAUDE.md:30-33
  - rules.py:110, 333-336 and 454-459
  - core.py:479-485
  - research/pyrel_cheatsheet.md sections 13-14
- **What goes wrong:** CLAUDE.md tells Claude to "add the rule on top of the existing score". A Claude Code session that follows the loaded skills will plausibly hit traps that the cheatsheet lists, and none of them are in CLAUDE.md:
  - (a) **`X | 0` inside `define` silently produces no fact (cheatsheet 13.2).** The skill recommends `Entity.prop | default`. Suppose the session writes `define(Company.new_score(Company.score + (Company.warm_points | 0)))` or reuses the declared `warm_path_points` without the zero branch. The re-score then exists only for the two reached targets. The "new Tier A list" shows two names, with no error.
  - (b) **Mixed orderings fail.** `rank(desc(score), asc(name))` raises "Mixed orderings" (13.4).
  - (c) **`aggs.string_join` raises on legacy (13.3).** A session building a new `why` will reach for it.
  - (d) **The Finale names are traps.** `Company.finale_score`, `finale_tier`, `finale_rank`, `has_conflict` and `warm_path_points` are declared in core.py and visible in `inspect.schema(model)`. They stay empty unless `enable_finale()` runs. A session that finds and queries them gets empty frames. A session that defines into them and later calls the fallback in the same process gets duplicate rules. Constraints are discharged, so conflicting values for a Property are kept silently.
  - (e) **A new ScoreComponent is silently not counted.** A session that copies the obvious ScoreCandidate/ScoreComponent pattern still needs `ScoreComponent.pillar`, `code_order` and `why_text`. Only the `_ACT1_CODES` loop sets those (rules.py:454-459), so without them the new component never enters `access_points`, `score` or `why`.
- **Result:** the Finale is meant to be the moment where reasoners compose, but it depends on Claude avoiding three silent traps under time pressure (see also R19d M5).
- **Fix:**
  1. Add a public, documented extension point to rules.py, for example `add_score_component(code, label, pillar, points, conds, evidence, order)`. It should wrap `_candidate(...)` and also define `pillar`, `code_order` and `why_text` for the new code. That way access_points, score, tier, score_rank and why all update declaratively. The Finale rule becomes about six lines, for example `add_score_component("A_WARM_PATH", ..., (EligibleTarget(Company), Company.current_ceo(p), p.nearest_seed_hops <= 2), ...)`.
  2. Add a short "PyRel on this install (1.27.1, legacy compiler)" block to demo_workspace/CLAUDE.md:
     - no `| default` inside define (use a second rule with `model.not_`);
     - all rank keys ascend (negate numbers);
     - no string_join;
     - dates come from `std.datetime`;
     - query `finale_*` only after `rules.enable_finale()`;
     - use `add_score_component` for new points.
  3. Keep a pre-tested `scratch/finale_check.py` that asserts the golden Finale set, so Claude can verify its own result before presenting it.

## MINOR

### m1. MINOR - The deprecated `filter_by` is the binding idiom throughout core.py

- **Where:** core.py:204, 218-331 (about 50 calls). The module docstring at line 21 also teaches it to any session that reads the file.
- **Evidence:** in 1.27.1, `Concept.filter_by` emits a `DeprecationWarning` ("use lookup") and constrains the concept's base variable, while `lookup` uses a fresh ref (frontend/base.py:1881-1935 and 1938-1959). The existing calls are safe, because each statement uses each concept once.
- **Risk:** a live session that copies the pattern into a rule that also mentions the bare concept will unify the two variables without meaning to.
- **Fix:** after the demo, migrate to `Concept.lookup(id=...)` and verify the entity counts on the engine (the cheatsheet marks lookup UNVERIFIED). For now, change the core.py:21 docstring to point to `lookup` for new code.

### m2. MINOR - KnowsEvidence keys can collide, which gives silent duplicate strengths and labels

- **Where:** rules.py:620, 586 and 599
- **Collisions:**
  - K3 uses `key="crm"` per (lo, hi). If two seeds logged positive interactions with each other, the two directions produce different counts, strengths and labels for the same identity.
  - K2 uses `key=t.id`. Two lead parties of one person on a deal, or a counterparty who held both CEO and CFO on the closing date, give two labels for one identity.
- **Why it is silent:** Property dependencies are not enforced, so `Knows.evidence` argmax still works. KnowsEvidence rows, though, can carry two labels.
- **Fix:** use `key=strings.concat("crm:", s.id)` for K3 and `strings.concat(t.id, ":", tp.id, ":", xr.id)` for the second K2 rule.

### m3. MINOR - The K3 label says "positive meetings" but counts every channel

- **Evidence:** `window()` counts calls, emails and conferences as well as meetings.

### m4. MINOR - The Q-FLOW `why` misstates betweenness

- **Where:** queries.py:392-393: "({x} shortest deal-flow paths run through it)"
- **Evidence:** unnormalized betweenness is a sum over firm pairs of the fraction of shortest paths through the node, and it is often fractional (the values match networkx `normalized=False`). "1,234.5 shortest paths" invites a correction from anyone technical.
- **Fix:** "betweenness 1,234.5 (summed over firm pairs, the share of shortest deal-flow connections that pass through it)".

## Determinism review

- **Ranks:** every `rank()` ends on a unique key. The keys are:
  - `score_rank` / `finale_rank`: id
  - `Knows.evidence`: kind, key
  - `closest_intermediary` and tie positions: id, key
  - `WarmPath`: route
  - `bridge_rank`: name, id
- **Floats:**
  - Path strengths are products in a fixed order, so they are IEEE-repeatable.
  - Betweenness is ranked on a 3 dp rounding, which is right given the engine's ~5e-9 relative difference from networkx. The residual risk is a value within 5e-9 of a rounding boundary, which is negligible.
- **Pivots and seeds:**
  - `num_pivots=16000` is at least |V| (160 deal-flow nodes), so betweenness is exact Brandes (graph/core.py:5070-5090). `validate_graphs()` guards it.
  - Louvain is seeded (42). PageRank is iterative, at tolerance 1e-6, and display only.
- **Tests:** tests/test_hero.py:153 checks determinism within one session only. Cross-process determinism rests on `export --compare`. Add one cross-process comparison of `tests/out/hero_outputs.json` to `make test`.

## Rules and graph: real work or SQL in disguise

| Piece | Verdict |
|---|---|
| Sector/region closure + nested exclude (rules.py:204-216, 265-270) | Real recursion and negation. A depth-3 tree is CTE-able, and QUESTIONS.md says so honestly. |
| R_CFO_FROM_PE three-way dated join (rules.py:370-383) | A real temporal composition. Single-statement SQL could do it, but it is reused across questions. |
| Knows from K1/K2/K3 (rules.py:540-641) | Real composition feeding a graph. The 365-day overlap correctly rejects the shared-employer decoy. |
| Warm paths (graphs.py:123-233) | Graph BFS from seeds and decision-makers, then fixed-depth (1-3) unrolled joins to enumerate routes. Honest framing: "graph distance finds the shortest length; rules enumerate and rank the routes". Not "variable-length path search". |
| Deal-flow betweenness + CoverageGap (graphs.py:289-308, rules.py:717-737) | The strongest graph-feeds-rule piece. It is a global property, not a count. |
| Conflict reach (graphs.py:332-345, rules.py:751-778) | Graph distance capped at 2 by the rule. A 2-hop self-join could do it, but the graph earns its place through the 3-hop bound check and the explicit route evidence. |
| Finale (rules.py:815-867) | Graph output (nearest_seed_hops) composing into a rule: correct. The conflict part is a plain join (see m10). |
