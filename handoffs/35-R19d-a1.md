## Findings

### B1 BLOCKER - The warm-up timing guarantees a suspended engine at Act 1
- RUNBOOK step 3 and the script's "Before you start" both say to run `make warm` 30 minutes before the meeting. The engine auto-suspends after 30 idle minutes (CONFIG, handoff 06).
- Warm ends at about T-27. Intros, the cold open and the explorer overview add no queries, so the engine suspends at about T+3, which is exactly when Act 1 starts.
- Act 1 then pays for an engine resume (minutes; R01 never measured it), plus about 50 s of engine init, plus 45-75 s of per-process compile. The Q&A also needs the engine.
- Fix (RUNBOOK.md and artifacts/demo_script_template.html "Before you start", owner R14/R16):
  - Run `make warm` once at T-30 to surface problems.
  - Run it again at T-10 or later.
  - Never let more than 25 minutes pass between the last query and Act 1.
- Fix (Makefile, owner R14): add a `make keepalive` target that runs one cheap query every 10 minutes until Ctrl-C. Start it after warm, stop it after the Q&A, then suspend. This keeps the 30-minute auto-suspend CONFIG intact.

### M1 MAJOR - Per-act latency will likely exceed the 90 s target, and Claude Code's Bash timeout is 120 s
- The first query of every new Python process costs 45-75 s even with a warm engine (handoffs 20, 23; Scout says 44-72 s while streams sync). Each live act runs `uv run python ask.py <fn>` as a new process. `make warm` runs everything in one process, so it does not remove that per-process cost.
- Add Claude's own turn time (skill load, reasoning, formatting) and the extra queries in q_path and q_conflict (3-12 s each). The 90 s target is at risk on every act, and no rehearsal timing exists.
- raiconfig has `wait_for_stream_sync: true` and `query_timeout_mins: 10`, so a stream re-sync after a reload can hang a call for 1.5-2.5 min (handoff 14).
- Claude Code's default Bash timeout is 120 s. A slow call gets killed or moved to the background, and Claude then retries on stage.
- Fixes:
  - demo_workspace/.claude/settings.json (R14): add `"env": {"BASH_DEFAULT_TIMEOUT_MS": "300000", "BASH_MAX_TIMEOUT_MS": "600000"}`.
  - pe_deal_graph/queries.py and ask.py (R11/R14): measure where the 45 s goes. If it is client-side compile, add a persistent local query server. `make warm` starts it, it keeps the model compiled in one process, and `ask.py <fn>` sends requests to it, falling back to in-process. If the time is engine-side, document it in the script's per-act timing.
  - R17 must report the median warm latency per act. The script must show the presenter a filler line for the first 60 s of each act.

### M2 MAJOR - The PAT expires 2026-10-29, and nothing checks it
- raiconfig uses `authenticator: programmatic_access_token` with `token_file_path: ~/.snowflake/pat_token_pe_demo`. The PAT was created on 2026-10-22 with a 7-day life.
- Neither the RUNBOOK nor the script mentions expiry. A demo on or after 2026-10-29 fails on every live act.
- `make warm` hides the cause: `rai reasoners resume ... >/dev/null 2>&1` falls through to the generic message "engine not READY".
- Fix (Makefile `warm`, R14): first run `$(RAI) connect`. On failure, print "make warm: FAIL - Snowflake auth failed (PAT expired? created 2026-10-22, 7-day life). Regenerate it in Snowsight as RAI_DEMO_PE's user and write it to the token_file_path in raiconfig.yaml".
- Fix (RUNBOOK.md, R14): add "PAT expires 2026-10-29: rotate it the day before any later demo" to the presenter checklist.
- Also run `chmod 600 ~/.snowflake/pat_token_pe_demo`. It is still 0644 (handoff 06 MINOR, unresolved).

### M3 MAJOR - The venue network is a single point of failure for every live act, with no plan
- Claude Code needs the Anthropic API, and RAI needs Snowflake. By default, Snowflake allows a PAT only for a user covered by a network policy. If that policy allowlists office or VPN egress IPs, the customer's guest Wi-Fi fails auth even when the PAT is valid.
- Nobody has verified which network policy applies to the PAT user.
- Fix (RUNBOOK.md presenter checklist, R14):
  - Check the PAT user's network policy and authentication policy once (Snowsight, ACCOUNTADMIN, outside the demo path).
  - Run `make warm` from the venue network, or from a phone hotspot, the day before or at T-30.
  - Keep the hotspot as backup. If a VPN is required, connect it before warm.
  - If the network is lost, go to fallback 3 (explorer) immediately. Do not retry live.

  - It has no URLs, no fetch and no localStorage.
  - It includes the Scorecard Finale toggle, the conflict view and a hidden #addon tab.
- Fixes:

  - Insert `--from-exports` as fallback step 2b in RUNBOOK.md and build_script.py `fallback_steps` (R14/R16).

### m1 MINOR - Permission gaps and first-launch prompts can appear on stage
- The allowlist in settings.json covers `uv run`, Read, Glob, Grep, Skill, ls, cat, head, grep and Edit(./scratch/**). It lacks `tail`, `wc`, `sed -n`, `cd` and `sort`, which Claude often adds when it pipes ask.py output.
- macOS has no `timeout` binary, so if Claude reaches for it, that call fails.

- Fix (settings.json, R14): allow `Bash(tail:*)`, `Bash(wc:*)`, `Bash(sort:*)` and `Bash(sed -n:*)`.
- Fix (RUNBOOK.md): at T-15, run `cd demo_workspace && claude`, accept trust, and run one throwaway prompt (`uv run python ask.py --list`) so the trust, plugin and skill-index steps happen off stage. Keep that session open for the demo, then `/clear`.
